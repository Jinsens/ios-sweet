# 2026-11-10 iOS-on-Android 显示与帧率

## 零拷贝扫描输出已验证正确（2466–2468）
- 内核在 present 后把"面板正在扫的那块 surface"采样成 80x178 缩略图（FBIMG 十六进制行），
  用 `tools/sweet-fbimg.py` 解码成 PNG：`research/matisse/20261109-resident-gpu/shim2468-ui/gpu-normal/fbimg/`
  里是正常的 iOS 桌面（设置列表、主屏/状态栏/dock），**横条花纹消失**。
- surface 必须物理连续（`sweet_surface_phys_runs`/`contiguous`），OVL 用 34 位地址（ADDR_MSB=0xf4c）。
- 每帧 present 现在 15–20 us（原来整屏 CPU memcpy 159–223 ms）。

## 帧率瓶颈的实测分解（2468/2470/2472）
- 帧间隔中位 ~60 ms（≈16 fps）；GL 每帧约 27 ms，其中等 GPU 2.5 ms；
  attach 阶段稳定 22 ms（每次 attach 都新建 18.4 MB 纹理 + 导入 surface + 全屏 blit）。
  `glTexImage2D 1440x3200` 单次 20–72 ms（已能跳过尺寸相同的重建，attach 未降）。
- 面板传输 **8.82 ms/帧**（`send 8819/8820 us`，极稳定）——这是"黑条闪烁"的来源：
  传输在面板扫描中途开始，屏幕上一半旧帧一半新帧。
- 排除项：同 surface 连发 `same 0`；控制台抢面板 `console 4`（已加锁，不再抢）；
  传输互相等待 `wait 0`。

## 2473/2474 的方向
- 2473：让 mutex 的 SOF 启动传输 → `sof 0/216`，2 ms 内没有启动，全部回退手写 DSI_START。
- 2474：等面板 TE（DSI_INTSTA bit2 TE_RDY）再启动传输，并测 TE 周期；
  若 TE 可用，传输就能对齐到面板帧起点，黑条应消失。

## 每帧 18.4MB 缓冲区复用（2475–2477，已提交 124d863）
- 实测量出根因（2475 console）：`SWEET SURF: slow buffer 18432000 bytes alloc 12983 us zero 790 us`
  和 `slow glTexImage2D 22531`。**贵的是找连续物理页，不是清零**：连续 18.4MB 分配 2.6–19.7ms，
  bzero 只有 0.8ms；纹理 BO 每帧 22ms。二者都是每帧新建、下一帧就丢。
- 改动：SweetSurface 按 (大小, task) 缓存释放掉的缓冲区，同 task 复用不再清零；wired 预算跟着
  缓冲区走（2475 就是没跟、约 41 帧后预算耗尽、8 次 0xe00002bd）；SweetGPU 每个 VM 缓存关闭
  BO 的 backing，复用前重新清零；gpu_vm_map 改成按物理段一次 getPhysicalSegment + 每段一次 dsb。
- 结果（最忙 10 秒窗口，跨轮可比）：2474 15.3fps → 2476 21.9fps / 2477 20.0fps；
  present 8835us → 16.7us/帧；vsync tick 19.04ms → 17.65ms；单帧总成本 49.2ms → 37.3ms。
- 注意：run 尾段会被空闲拉低（2476 尾段 35.7fps、2477 22.7fps，工作量相同），只能用最忙窗口比。
- 剩余瓶颈：attach 仍 ~9.6ms/帧 —— 每帧新 surface ⇒ 新 import + 18.4MB 的 VM_BIND + unmap，
  每次都以 `sweet_csf_runtime_invalidate`（LOCK/INVALIDATE_ALL/UNLOCK 三条 AS 命令、等待地址
  空间空闲）收尾，把 CPU 和 GPU 每帧串行化一次。下一步从这里下手。

## 壁纸根因（不是 Metal）与帧耗时再定位（2478–2482）
- 内核加了 patch 0216：崩溃时用 dyld_all_image_infos 报出 pc 落在哪个镜像，输出
  `CRASH <name> image <path> + 0xoffset`。设备上的 .ips 在
  `/private/var/mobile/Library/Logs/CrashReporter/`，两者一致：
  `PosterBoard.framework + 0x1d268` = `-[PBFPosterExtensionDataStore
  _stateLock_setupSwitcherConfigurationForFirstTime] + 2040`。
- 反汇编（设备自带 dyld cache 在 `/private/preboot/Cryptexes/OS/System/Library/Caches/com.apple.dyld`，
  44 片 3.1GB，复制到可写目录后 `ipsw dyld disass` 可用）看到断言字符串
  `"Invalid condition not satisfying: !_stateLock_switcherConfiguration"`。
  路径：prewarm → updateExtensions → 取不到任何 poster 配置 → 建默认 switcher 配置时断言失败。
- `sweetiolog=PosterBoard` 显示崩溃前**没有** AGXAccelerator/IOAccelerator 匹配，只有
  /product、/arm-io/disp0、AppleCLCD、AppleKeyStore —— “壁纸要 Metal”这条旧假设对这个崩溃不成立。
- 数据存储 `PRBPosterExtensionDataStore/59` 是空的（只有空 Extensions/、GalleryCache/），
  说明非空的 `_stateLock_switcherConfiguration` 是本次运行里造出来的，指向“没发现任何 poster
  扩展被注册”，下一步应查 pkd/LS 的扩展注册，而不是继续猜 Metal。
- 帧耗时：2480 逐调用计时（每 200 次平均）推翻原判断——`map ptes` 2.7–3.3ms、`unmap` 1.5–1.9ms，
  而一直被当成串行点的 AS 失效只有 **7us**。真正原因是页表内存按 write-combined 映射：
  读一个 PTE 比写还贵，而 map 路径每页读两遍。
- 2482 改成只写不读（占用探测改走 BO 表）+ 页表按地址缓存：map 降到 1511us，
  最忙 10 秒 24.6fps（2480 23.2、2481 19.1）。unmap 仍 1860us，因为剩下的就是写本身。
- 下一步：页表改可缓存（写后 dc civac 再让 MMU 走）或用 2MB 块描述符，二选一、单独试验。
- 清理：/tmp/dscopy（3.1GB 缓存副本）已删；需要时从上面路径重新复制即可。

## 扩展注册全线失败（壁纸+小组件同因）与"没有软件渲染"（2483）
- 结论：**没有任何 app extension 注册成功**。设备 root 里 140 个 App 全部在 lsd 数据库，
  131 个 appex 只有 **2** 个在；整个 boot 只创建了 1 个 PluginKitPlugin 数据容器
  （AuthenticationServicesUI.AccountAuthenticationModificationExtensionHelper，正好是带 .appexpt 的那个）。
  pkd 在跑（launchd.log "Successfully spawned pkd[189] because ipc (mach)"，之后无退出），但容器是空的。
- LS 库位置：`/private/var/mobile/Containers/Data/InternalDaemon/B4392D64-…/Library/Caches/
  com.apple.LaunchServices-4035-v2.csstore`（3.5MB），旁边有 SystemDataOnly 版。
- 每个 appex 被丢弃的原因（设备自己的 tracev3 里，只能 strings——这版 iOS 的条目 host `log` 解不了）：
  "NSExtensionPointIdentifier … does not correspond to a known extension point"，
  来自 `+[MILaunchServicesDatabaseGatherer enumerateAppExtensionsInParentID:…]`。
- 反汇编 `-[MIPluginKitBundle overlaidInfoPlistWithError:]`（0x1b11d4acc）确认门槛是
  `extensionPointOverlay` → `extensionCacheEntryWithError:` 返回 nil。扩展点是 LS 记录
  （`_LSDModifyClient registerExtensionPoint:platform:declaringURL:withInfo:`）；
  /Applications 扩展用到的 29 个扩展点里库中只有 4 个，`com.apple.posterkit.provider`、
  `com.apple.widgetkit-extension` 都不在 → 壁纸/小组件同一个原因，**不是 Metal**。
- 排除项：`/System/Library/ExtensionKit/ExtensionPoints` 只有 6 个 .appexpt，原厂 IPSW 也只有 6 个；
  App cryptex（087-86715-047.dmg → /Volumes/AppCryptex）只有 Safari，没有 .appexpt。所以不是缺文件。
- 软件渲染排查（2483 = 2482 + `gltrace=200-260 gltrace_place=1`）：60 帧、1017 次 draw 里
  **只有 1 次** CPU 上传（180×179，128KB）。renderer 自报 `Mesa 25.0.7; Mali-G710 (Panfrost)`，
  模糊是 fragment shader，帧行显示 "0 textures refilled"、"0 pictures copied out"，面板 copies 0、
  present 17us。→ **光栅化在 GPU，没有软件渲染**。
- 真正的剩余成本是 GL 调用的 CPU 侧：动画帧 220 是 1048 calls / 202 draws / 49717us，
  其中等 GPU 2353us、提交 331us ⇒ 约 **45us 一次调用**。下一步用 `glslow=US` 或 `glcensus=1` 定位。

## 帧耗时到底花在哪（2484–2486）
- 2482 的 65 条帧线拆分：**GL 调用本身 68.6%**（中位 32.8µs/次）、attach 21.4%、
  等 GPU 9.0%、提交 1.0%、回读 0%。所以不是软件渲染，是 CPU 侧的 GL 调用成本。
- 2484：把提交路径里的调试 `IOLog("SWEET GPU: ping")` 去掉（2482 里 77977 行、占 console 93%，
  而且每行都在持 gpu_lock 时写）。**帧率无变化**（85.8 vs 84.6 µs/次调用），但 console 干净了。
- 2485：内核侧计时——**submit 平均 7µs**（max 17），**wait 平均 376µs**（max 2504）；
  ~500 帧里 9600 次 wait ⇒ 每帧约 19 次、**7ms/帧**。来源是用户态 pending 队列只有 24 深
  （redwood_drm.c `pend_wait_head`），满了就同步等最老的一次提交。
- 2486：内核没有设置任何处理器时钟。用 4M 次相关 add 探针测得 **~1250MHz**（1250/1250/1297/1250），
  而 A76 标称 2.2–2.3GHz ⇒ userland 只跑在一半频率上。这解释 32.8µs/次调用的量级，
  也是当前最大的一根杠杆（约 1.8x，24fps → 40fps 量级）。
- 下一步优先级：① CPU 频率（没有任何代码投票，停在 bootloader 留下的档位）；
  ② 减少每帧提交次数以消除 7ms 队列等待；③ attach 仍占 21%。
