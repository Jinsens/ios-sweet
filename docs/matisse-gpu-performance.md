# matisse GPU 性能排查（2026-11-13）

## 已实测的改善：2520

设备为 MT6983 / Mali-G710，UI 使用 Mesa Panfrost 硬件渲染。用户在 2520
临时启动测试中确认“明显更流畅”；测试后完整 boot_a 备份已恢复并独立读回验证。

| 相同操作或工作量 | 原版 | 2520 | 含义 |
|---|---:|---:|---|
| map 累计第 1000 次平均 | 1462 µs | 39 µs | 按 L3 表跨度处理，减少慢速非缓存读取 |
| unmap 累计第 800 次平均 | 1991 µs | 14 µs | 同一张表只查找一次 |
| 地址空间失效平均 | 6 µs | 6 µs | 此处并非主要瓶颈 |
| 6 draws / 65 GL calls 帧中位数 | 6559 µs | 5317 µs | 样本分别 20 / 19，表面准备 3073.5 → 361 µs |
| 25 draws / 179 GL calls 帧中位数 | 10401 µs | 8670 µs | 样本分别 6 / 7，表面准备 3257.5 → 267 µs |

日志含用户不操作时的长空档，不能用整段平均 FPS 比较速度。GL 帧时间也不等于
面板扫描输出时间。当前测量没有证明持续 120 FPS。

## 剩余瓶颈与新修正

2520 的复杂 UI 样本仍需约 14–26 ms，帧末等待约 1.4–4.4 ms，表面准备约
0.2–0.8 ms。帧内 GL 调用包含提交和提前等待，不能把其余时间都归为 CPU 运算。
累计 9800 次内核 wait 平均 459 µs，说明等待仍有相当成本。

只读检查 `live-root-gpu2473.dmg` 中实际安装的 Mesa，确认
`drmSyncobjTransfer` 在复制源栅栏时调用 `fence_wait`。历史追踪中，1736 个
submit 段有 1727 个在下次提交前出现 transfer 和 wait；追踪跨越历史启动且
每进程截断，因此不能据此计算 2520 的逐帧等待原因比例。早先把这些等待全部
归因于队列满的判断需要撤回。

配套检查发现，内核 `enqueue` 要求 `extract == insert`，同样阻碍多个批次在途。
优化必须同时维护两端的契约：

1. 内核根据空余字节接收提交：4 KiB 命令环，每批 128 B，保留一格，最多 31 批。
   读取 64 位 extract 时检查高字稳定，拒绝损坏的游标。队列满返回可重试 Busy，
   保留原序号、原命令和健康 VM。
2. 传输层复制不可变的硬件 fence 标识，保留引用，延迟到真正使用资源时等待。
   源 syncobj 的销毁、重置或编号重用不能改变已经复制的依赖。跨组、非单调
   提交保留保守等待；GPU 故障不能被当作成功完成。
3. 每个 queue submit 都限制待回收项，包含一次 ioctl 中的多项提交；调试文件
   追踪仅由 `gputrace=1` 显式开启。

两端实现已完成：内核提交 `904b17c`，传输层提交 `dcb67bb`。16 项真实 C
传输层测试和 4 项内核 C/C++ 测试全部通过 ASan/UBSan，包括复制后源对象
重置/销毁/复用、多点时间线、多输出、批量容量、连续 Busy、失败完成和超时。
所有输出分配和顺序等待都在硬件接受任务前完成；接受后的发布不再分配或等待。

完整 iOS arm64 Mesa 和内核构建均成功，库的签名与依赖检查通过。候选 2521
同时保留 2520 映射优化及已在设备验证的 2518 防闪修复，明确使用
`sweetfb_syncswap=1 sweetfb_vendor=1 sweetfb_hold_us=14500 sweetfb_lead=300`、
原生 60 Hz。构建包及精确哈希保存在 NOTES.md 指向的本地清单中。
这些是已定位的串行点及代码修正，新版尚无硬件 FPS 结果。

## 60 / 120 测试软件

`userland/gpu-bench` 提供两个目标帧率。实际统计 512×512 离屏着色器工作负载
在 `glFinish` 成功后完成的帧，显示目标丢失、完成时间分布和 JSON 导出。
首次着色器预热、颜色读回校验排除在计时外。应用尚未在设备上启动。

120 FPS 的预算为 8.33 ms。提高测试目标不会把面板切到 120 Hz；真实屏幕
120 Hz 需要厂商面板模式序列、正确的 TE 周期和扫描输出验证。显示线程等待
与传输时序另有独立工作，不应靠更快计时器掩盖。
